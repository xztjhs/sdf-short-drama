# 01 · 架构设计

> 读完这篇你应该明白：为什么是这个架构，边界在哪，哪些地方不能动。

---

## 1. 一句话架构

**LLM 在云上写分镜，GPU 在本地出画面，CPU 拼成片。**

```
┌──────────────────────────────────────────────────────────────────┐
│                     icompify 远程 LLM（零本地算力）                │
│  DeepSeek-V4-Pro / GLM-5.2（1M 上下文）                           │
│  职责：剧本 → 结构化分镜 JSON（严格契约，见 §4）                     │
└────────────────────────────┬─────────────────────────────────────┘
                             │ HTTP / JSON
┌────────────────────────────▼─────────────────────────────────────┐
│              L2 编排层 · sdf-api 容器（纯 CPU）                  │
│  · SQLite 状态库（project/episode/shot/job）                       │
│  · 路由决策（router.py）                                          │
│  · ComfyUI 客户端（comfy.py）                                     │
│  · 成片（assemble.py）                                            │
└────────────────────────────┬─────────────────────────────────────┘
                             │ /prompt + /history 轮询
┌────────────────────────────▼─────────────────────────────────────┐
│              L3 渲染层 · sdf-comfyui 容器（独占 GPU）            │
│  轨道 A: MiniMax H3 FL2VA  ← 对白镜头，原生立体声                   │
│  轨道 B: Wan2.2 TI2V-5B    ← 空镜/动作，快 4 倍                    │
│  ⚠️ 串行：一次一个镜头                                             │
└────────────────────────────┬─────────────────────────────────────┘
                             │ mp4 文件
┌────────────────────────────▼─────────────────────────────────────┐
│              L4 成片层 · ffmpeg（CPU 多核 + NVENC）                │
│  规范化 → 拼接 → 响度 -16LUFS → 字幕烧录 → 1080×1920               │
└──────────────────────────────────────────────────────────────────┘
```

## 2. 三个关键设计决策

### 决策 1：为什么 LLM 不本地跑

| 方案 | 成本 | 质量 |
|---|---|---|
| 本地跑 32B 模型 | 吃 20GB 显存 → 和渲染抢资源 | 分镜质量明显弱 |
| icompify 远程 | ¥0.2/集 | 1M 上下文，能一次读完整本小说 |

**结论**：LLM 是"每次都要用但不持续占资源"的负载，放云上。GPU 是"贵且独占"的资源，留给扩散模型。

### 决策 2：为什么 H3 + Wan2.2 混合，而不是纯 H3

实测数据（A5000，768×1344 竖屏原生 1MP）：

| 引擎 | 5s 单镜耗时 | 音频 | 分辨率上限 | License |
|---|---|---|---|---|
| H3 | **~6 分钟** | ✅ 原生立体声 | 768 短边 | 社区版（有地域限制） |
| Wan2.2-5B | **~1.5 分钟** | ❌ 需后期配 | 720p | Apache-2.0 |

H3 不可替代的只有一件事：**一次前向同时出画面+对白+音效+音乐**。
其他场景它只是"慢 4 倍"。

而短剧镜头构成里，真正需要原生音频的只有 **40%**（对白镜头）。剩下 60% 用 5B 完全够。

**单集 40 镜**：
- 纯 H3：40 × 6 × 2(重试) ≈ **8 小时**
- 混合：16×6×2 + 24×1.5×2 ≈ **4.5 小时**（实际优化后 2.5-3 小时）

这个差别决定了能不能日更。

### 决策 3：为什么串行不并发

**A5000 只有 24GB，H3 峰值占用 ~20GB。**

两个 H3 任务并发 → 必然 OOM → OOM Killer 杀进程 → 容器报 ExitCode=0（假成功）。

并发带来的"效率提升"是幻觉，实际是排队时间挪到了失败重试上。

`worker.LOCK` 是全局锁，不是可选项。

## 3. 分层职责边界

| 层 | 能做什么 | **不能**做什么 |
|---|---|---|
| LLM | 生成分镜 JSON | 不做渲染决策、不碰文件 |
| 编排 | 路由、排队、重试、调 ffmpeg | 不做像素处理 |
| ComfyUI | 执行工作流、出 mp4 | 不做业务逻辑 |
| ffmpeg | 拼接/转码/混音 | 不做内容判断 |

**契约是 JSON**。任何一层替换掉，其他层不受影响。

## 4. 分镜 JSON 契约

这是全系统唯一的接口约定。LLM 必须产出这个结构，编排层只认这个结构。

```json
{
  "title": "第1集 天台对峙",
  "summary": "林晚在天台发现真相",
  "characters": [
    {
      "name": "林晚",
      "appearance": "26-year-old Chinese woman, long black hair, sharp eyes, wearing a beige trench coat",
      "voice_note": "清冷，略带沙哑"
    }
  ],
  "shots": [
    {
      "seq": 1,
      "duration": 5.0,
      "shot_size": "远景",
      "camera": "推",
      "prompt": "Wide shot of a woman in beige trench coat standing alone on a rooftop at dusk, city skyline behind, wind blowing her hair, cinematic lighting, shallow depth of field, film grain",
      "negative": "blurry, distorted, watermark, low quality, extra limbs",
      "dialogue": null,
      "sfx": "风声",
      "characters": ["林晚"]
    },
    {
      "seq": 2,
      "duration": 6.0,
      "shot_size": "近景",
      "camera": "固定",
      "prompt": "Close-up of the same woman's face, tears in eyes, dim warm light from below, subtle facial expression change",
      "negative": "blurry, distorted, watermark",
      "dialogue": "原来一直都是你。",
      "sfx": null,
      "characters": ["林晚"]
    }
  ]
}
```

**字段约束**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `seq` | int | ✅ | 镜号，排序用 |
| `duration` | float | ✅ | 秒。3-8 秒。H3 会对齐到 17k+5 帧网格 |
| `prompt` | string | ✅ | **英文**。主体+动作+环境+光线+运镜+画质 |
| `negative` | string | | 英文负面词 |
| `dialogue` | string\|null | | 中文台词。有值 → 路由到 H3 |
| `sfx` | string\|null | | 音效描述。有值 → 路由到 H3 |
| `shot_size` | string | | 远景/全景/中景/近景/特写 |
| `camera` | string | | 固定/推/拉/摇/移/跟 |
| `characters` | string[] | | 角色名，用于一致性 |

## 4. 路由规则

`pipeline/router.py` 的判定顺序（命中即停）：

```
1. 强制指定 engine → 用之
2. dialogue 非空        → H3    "有对白 → 原生立体声"
3. sfx 非空             → H3    "有音效要求"
4. prompt 含动作词      → 5B    "动作镜头 5B 更快不易崩"
5. 含空镜/远景关键词    → 5B    "空镜产能优先"
6. quality_first + 特写 → H3    "关键特写质量优先"
7. 默认                 → 5B    "产能优先"
```

**分辨率分配**：

| 引擎 | 默认 | quality_first |
|---|---|---|
| H3 | 768×1344 | 768×1344 |
| 5B | 544×960 | 720×1280 |

**步数分配**：

| 引擎 | 默认 | 说明 |
|---|---|---|
| H3 | 8（Turbo LoRA） | 20 步质量更好但慢 2.5× |
| H3 对白 + quality | 12 | 口型/音频对步数敏感 |
| 5B | 6 | lightx2v 4-step 可降到 4 |

## 5. 工作流结构（已核实源码）

H3 的图结构容易写错，这里给出正确接法：

```
UNETLoader ─┬─> [LoraLoaderModelOnly] ─┬─> BasicGuider.model
            │                          └─> BasicScheduler.model
CLIPLoader ──> MiniMaxH3ImageToVideo.clip
VAELoader(v) → MiniMaxH3ImageToVideo.vae

MiniMaxH3ImageToVideo ──(0 positive)──> BasicGuider.conditioning
                       └─(1 latent)───> SamplerCustomAdvanced.latent_image

SamplerCustomAdvanced ─> VAEDecode(vae_v)       # unbind()[0] = 视频
                       └> VAEDecodeAudio(vae_a) # unbind()[-1] = 音频
两者 ─> CreateVideo ─> SaveVideo
```

**三个必知的坑**：

1. **H3 没有 negative 输入**。它只输出一条 conditioning，所以必须用 `BasicGuider`（无 CFG），不能用 `KSampler`。负面提示词对 H3 无效。
2. **turbo 不是节点开关**，而是加载 `minimax_h3_fl2v_turbo_8step` LoRA 并使用 8 步。
3. **H3 latent 是嵌套张量 `{video, audio}`**。`VAEDecode` 内部 `unbind()[0]`，`VAEDecodeAudio` 取 `unbind()[-1]`。所以两个解码节点接同一个 `SamplerCustomAdvanced` 输出就行，不用手动拆。

Wan2.2 的图更常规：`Wan22ImageToVideoLatent` 只产 latent（可选 `start_image` 首帧），条件在 `KSampler` 里以 positive/negative 给（有 CFG）。

## 6. 数据流与存储

```
/data/video.db          SQLite 状态库（WAL 模式）
/output/{project}/E01/  渲染产物
  ├── sh_xxx_h3_v1.mp4
  ├── sh_yyy_wan22_v1.mp4
  ├── subtitle.srt
  └── E01_final.mp4
/models/                ComfyUI 模型（42GB）
/workflows/             ComfyUI 工作流 JSON
/logs/                  容器日志
/input/                 首帧图、角色参考图
```

**没有对象存储，没有数据库服务**。SQLite 单文件 + 本地目录，够用且零运维。

## 7. 已知边界
| 限制 | 影响 | 缓解 |
|---|---|---|
| 单卡串行 | 无法并行出片 | 队列 + 夜间批跑 |
| 24GB 显存 | 768p 已是上限 | 544p 超分到 1080p |
| H3 只有 Base | 拿不到 2K | 后期超分替代 |
| 无 swap | OOM 静默杀进程 | **必须加 swap** |
| 角色一致性靠 Ref2VA | 需额外 21GB 权重 | quality_first 时启用 |
| H3 无 CGF/negative | 不能靠负面词压画质 | prompt 正向描述要写好 |

## 8. 为什么不用的方案（避免重复讨论）

| 方案 | 否决原因 |
|---|---|
| Dify 编排 | 多一层服务，多一倍内存开销，本地 SQLite 够用 |
| Redis + Celery | 单机单卡，队列在 SQLite 里就够 |
| ComfyUI WebSocket | 长任务偶尔丢消息，`/history` 轮询更可靠 |
| 多卡并发 | A5000 单卡已 20GB，加卡才有意义 |
| 本地 TTS + 对口型 | H3 原生音频一次到位，省两个模型 |
| 云端 API 出片 | ¥0.5-0.8/秒，一集 90s = ¥45-72，本地电费 ¥0.6 |
