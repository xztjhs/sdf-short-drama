### 坑 17：`render()` 并发竞态——页面报 null，组合成片面板看着是空的（2026-10-24）

**症状**：控制台报 `Cannot set properties of null (setting 'innerHTML')`，
堆栈指向 `renderRender (.../:1521:16)`。同时「🧩 组合成片」面板明明是
17 个镜头，界面上却一个条目都没有。锁定页长期停在「加载中…」。

**根因**：`render()` 每次都用 `m.innerHTML=''` 清空 `#main` 再重建，
而 `renderRender` 是异步的：

```js
/* 当时 */
m.innerHTML = `<div id="vidGrid"></div> ...`;
await renderComposer(ep);      // 让出执行权
const g = $('#vidGrid');       // ← 此时可能已被新一轮 render 销毁 → null
g.innerHTML = ...              // 💥
```

`await` 期间，监视栏计时器（`setInterval(refreshSys)`）和队列计时器
（4000ms）触发的第二次 `render()` 会把整个 `#main` 清空重建，
旧的 `body` div 直接脱网，回来后的 DOM 查询全部为 null。

**解法**：加渲染代次守卫：

```js
let RENDER_GEN = 0;
function render(){
  const gen = ++RENDER_GEN;
  ...
  if(S.stage==='render') return renderRender(body,p,gen);
}

async function renderRender(m,p,gen){
  const alive = () => gen===undefined || gen===RENDER_GEN;
  ...
  await renderComposer(ep);
  if(!alive()) return;           // 过时就放弃，别碰已销毁的 DOM
  const g = $('#vidGrid');
  if(!g) return;                  // 双保险
```

`renderLocked` 同样在 `await` 后加了代次检查。

⚠️ **验证陷阱**：这个 bug 让「组合成片面板 0 条目」看起来很像是前端功能没写完，
我一度以为是 `renderComposer` 没被调用。实际用 `page.evaluate` 手动调一次
`await renderComposer(S.episode)` 就出 17 条——说明**函数本身好的**，
是渲染时序被覆盖了。以后碰到「DOM 看着是空但接口有数据」，
先手动调一次渲染函数对账，别直接怀疑业务逻辑。

### 坑 18：锁定页每次进都重算 LLM，卡 6.7-11.6 秒（2026-10-24）

**症状**：打开项目 → 点「锁定基础信息」，页面一直停在 `加载中…`，
`#main` 只有 1363 字节，无任何 JS 错误。

**根因**：`POST /api/projects/{pid}/extract-baseinfo` **无缓存无条件调 LLM**：

```python
@app.post("/api/projects/{pid}/extract-baseinfo")
def api_extract_baseinfo(pid: str, req: dict):
    data = llm.baseinfo(script_text)     # 每次 6.7-11.6s，还花钱
```

旧项目（v0.2 时代建的，如 `prj_baeff0aa66e5 最后一次值班`）
`locked_info` 是 `None`，所以就算已经跑到 `done` 了，
每次进锁定页还是让 LLM 重抽一遍同样的东西。

**解法**：三级降级，能省就省：

1. **已锁定** → 直接返回 `locked_info`（`cached: true`）
2. **旧项目**（`locked_info` 为空但库里已有角色+风格）
   → 用 `db.list_characters(pid)` + `project.style` 组装（`source: "project"`）
3. **实在没有** → 才调 LLM

要强制重算传 `{"force": true}`，界面上对应新加的「🔄 重新抽取」按钮。

实测：`6.674s → 0.012s`（约 550 倍）。

⚠️ 注意 `project` 表**没有** `characters` 列（角色在 `character` 关系表里），
直接用 `prj.get("characters")` 会拿到空列表，必须走 `db.list_characters()`。

### 坑 16：配置改了「没生效」——`--ignore-existing` 把正常发布也挡住了（2026-10-24）

**症状**：v0.6.4 的一批需求（11 个风格预设重写、`storyboard_v2` 八要素模板、
`assemble.subtitle` 字幕样式、routing 简化）在本地全改完了，代码也重建了容器，
但界面上一点变化都没有。API 返回的 `render` 字段还是 30 字的旧文案。

**根因**：`deploy/sync_deploy.sh` 对 `config/` 用的是
`rsync -a --ignore-existing`（只补远端缺失的文件，绝不覆盖）。
本意是保护「后台界面改过的运行时值」，但结果是**所有正常发布也被挡住**：
服务器 `config/` 一直停在 v0.2 基线。

```
本地 presets.yaml 8457 字节  →  服务器 5558 字节（v0.2 老基线）
本地 prompts.yaml 20448 字节 →  服务器 18593 字节
本地 settings.yaml 3787 字节 →  服务器 1155 字节（version 还写着 0.2.0）
```

这类 bug 最坑的地方：**改动在本地、在 git 里都是对的**，
单测/语法检查全绿，只有真去看线上 API 返回值才暴露。

**解法**：新增 `deploy/publish_config.py`，做**白名单式合并发布**，而不是整文件覆盖：

| 类别 | 策略 | 例子 |
|---|---|---|
| 内容库 | **以仓库为准** | 风格预设 `styles[].render`、`prompts.*` 模板 |
| 运行时参数 | **保留服务器值** | `assemble.orientation/width/height/fps`、`delivery_*`、字幕六项、`monitor` 监控栏 |
| 服务器独有键 | 补回本地缺失 | `assemble.delivery_width/height` |
| `secrets.env` | 完全不碰 | — |

实现要点：
- `settings.yaml` 走**文本补丁**（`patch_settings_text`），不用 `yaml.safe_dump`——
  否则会丢掉全部运维决策注释（v0.5 为何回 720p、`chain_frames` 为何关 R3、Ref2VA 说明）。
- 写前服务器 `cp -a` 留 `.bak.<时间戳>`，写后 YAML 自检 + 顶层键不许变少。
- 自检发现结构损坏就**跳过写入**（真拦下过一次：`delivery_*` 被插进 `subtitle:` 子块中间，
  YAML 直接解析失败）。

**正确用法**：

```bash
python3 deploy/publish_config.py --dry-run     # 先看会改什么
python3 deploy/publish_config.py               # 发布
python3 deploy/publish_config.py --rebuild     # 发布并重启 api
./deploy/sync_deploy.sh --rebuild --sync-config  # 代码+配置一起发
```

配置默认**不随代码自动发布**，避免误盖线上参数；要发就显式加 `--sync-config`。

**教训**：「保护性忽略」和「发布」是两件事，不能用同一个开关。
只要有一个 `--ignore-existing`，就永远无法通过 rsync 更新已有文件。

### 坑 15：H3 的节点签名与网上教程对不上（已核实并修正）

**症状**：按搜到的教程写工作流，提交报 `Prompt outputs failed validation`。

**根因**：`MiniMaxH3ImageToVideo` 的**真实签名**（已对照 ComfyUI 主线源码核实，2026-10-20）是：

```python
# comfy_extras/nodes_minimax_h3.py
inputs=[
    io.Clip.Input("clip"),
    io.Vae.Input("vae"),
    io.String.Input("prompt", multiline=True),
    io.Int.Input("width",  default=1344, step=32),
    io.Int.Input("height", default=768,  step=32),
    io.Int.Input("length", default=124,  step=17),   # 17k+5 网格
    io.Image.Input("first_frame", optional=True),
    io.Image.Input("last_frame",  optional=True),
]
outputs=[Conditioning(positive), Latent]
```

**关键事实（全部与网上多数教程不符）**：

| 我原以为 | 实际 |
|---|---|
| 有 `negative` 输入 | ❌ 没有。只有一条 conditioning → 必须配 `BasicGuider`，不能用 `KSampler` |
| 有 `turbo_mode` 开关 | ❌ 没有。turbo = 加载 Turbo LoRA + 用 8 步 |
| 有 `audio_vae` 输入 | ❌ 只在 Ref2VA 和 AddGuide 上有，FL2VA 没有 |
| 自己拼空 latent | ❌ 节点自己返回 `(cond, latent)`，latent 已是嵌套 {video, audio} |
| `num_frames` | 实际叫 `length`，且 `step=17`、`min=5` |

**正确的图结构**：
```
UNETLoader → [LoraLoaderModelOnly] → BasicGuider.model
                                    → BasicScheduler.model
CLIPLoader → MiniMaxH3ImageToVideo.clip
VAELoader(v) → MiniMaxH3ImageToVideo.vae
MiniMaxH3ImageToVideo → (0=positive) → BasicGuider.conditioning
                      → (1=latent)   → SamplerCustomAdvanced.latent_image
SamplerCustomAdvanced → VAEDecode(vae_v)      # 自动 unbind()[0] = 视频
                      → VAEDecodeAudio(vae_a) # 自动 unbind()[-1] = 音频
两者 → CreateVideo → SaveVideo
```

**验证**：`python -m pipeline.workflow` 会打印节点数并跑静态自检（检查有无孤连接、H3 帧对齐、缺 VAEDecodeAudio）。

**教训**：**不要抄博客。** 节点签名只能信源码或 `/object_info` 接口。

## 2026-10-20 · H3 在 24GB 卡上的五个坑（来自实测资料，未全部现场复现）

### 坑 1：`memory_usage_factor` 让显存分配器永不触发 offload

**症状**：24GB 卡，第一次跑就 `CUDA out of memory`，看不出任何内存压力。

**根因**：`comfy/supported_models.py` 里 `MiniMaxH3.memory_usage_factor = 0.114`。
这个值告诉 ComfyUI「H3 只用你显存的 1/9」，于是它把所有模型一次性全塞进显存，从不触发 CPU offload。

```python
# comfy/supported_models.py — class MiniMaxH3
memory_usage_factor = 0.114   # 改前：分配器以为 H3 很小
memory_usage_factor = 1.0      # 改后：采样前就会触发 offload
```

**解法（按顺序）**：
1. **先升级 ComfyUI 到 0.32.0+**（issue #15486 已修），多数情况不用手改
2. 仍失败才手工改成 `1.0`

**不要**同时加 `--lowvram`（与 `--disable-pinned-memory` 冲突）。

---

### 坑 2：进程无声消失，容器报 ExitCode=0

**症状**：渲染跑一半，任务没了。`docker ps` 显示容器正常重启过，`docker inspect` 显示 `ExitCode=0, OOMKilled=false`，日志里**没有任何 CUDA 错误**。

**根因**：**host RAM 被 OOM Killer 杀了**，不是显存。

`pinned memory` 不能被换页。24GB 卡上 H3 采样时只有 ~6.6GB 留在显存，其余 ~25GB 权重在 host RAM 里每步翻页。64GB 机器上其它容器占了 30GB 就会撞墙。

**诊断**：
```bash
dmesg -T | grep -i "oom-kill" | tail -20
# Out of memory: Killed process 12345 (python3) ...
```
`docker inspect` 在这里会撒谎——内核 OOM 杀进程时 Docker 报告 ExitCode=0。

**解法**：
```yaml
CLI_ARGS: --disable-pinned-memory    # 让权重可以被换页
```
+ 加 swap（64GB）+ 停掉其它吃内存的容器。

**实测对比**：同一次 3090 跑 15s 片段，不加 `--disable-pinned-memory` 峰值 29.8GB 被内核杀；加了之后峰值 7.5GB，23 分 17 秒完成。

### 坑 3：1-2 秒短片 OOM，10 秒反而正常

**症状**：短片段 OOM，长片段能跑完。反直觉。

**根因**：显存估算器在短时长上过度乐观。有报告显示它给 2 秒片段预算 5,100 MiB，实际保留峰值 28,928 MiB（卡只有 24,564 MiB）。到 10 秒估算够大，反而强制了完整 offload，就成功了。

**解法**：**先跑长的测试**。真要短片段，加个无关节点改变图结构。

（ComfyUI issue #15663）

---

### 坑 4：同一张图 OOM 过一次，就永远 OOM

**症状**：某个工作流 OOM 之后，同样的图再跑永远 OOM。重启 ComfyUI 无效，重启机器无效，`--cache-none`、`UnloadAllModels`、`ClearCache` 全无效，复制粘贴整张图也无效。

**根因**：坏预算被缓存在一个由「图结构 + 节点值」派生的 key 上，且**跨进程存活**。

**解法（荒谬但有效）**：**往画布上插一个任意无关节点**，或者改任意一个节点的参数。立刻恢复。

`worker.RETRY_STRATEGY` 就是按这个原理设计的——每轮换一个变量（seed / steps / 分辨率），不原样重试。

（issue #15663）

---

### 坑 5："Retrying with tiled VAE decoding" 是一句空话

**症状**：长片段在 decode 阶段挂了，控制台提示「retrying with tiled decoding」，然后同样挂掉。

**根因**：`MiniMaxH3VideoVAE.decode_tiled()` 内部直接调 `decode()`——同一个调用，同样的失败。H3 的 VAE 本身就内部 tile（256px 空间 / 17 帧时间），`handles_tiling = True`。

**解法**：在采样器和 decode 之间插一个 passthrough 节点调 `comfy.model_management.unload_all_models()`。有报告这样 243 帧 302 秒稳定完成。

（issue #15453）

---

### 坑 6：图生视频卡一分钟才失败

**症状**：文生视频加载 5 秒，同样的图加上首帧图后卡 1 分钟以上。

**根因**：`load_model` 只算了模型大小，没算图片。图片编码在模型已经驻留之后才超预算。

**解法**：`--reserve-vram 2.5`（已在 compose 里配好）。

（issue #15316）

### 坑 10：Unraid 重启后 `/usr/local/bin` 不持久

**背景**：Unraid 的根文件系统在内存里，`/usr/local` 重启就没了。`/boot/config/` 是持久的。

**解法**：
- 需要持久化的脚本放 `/boot/config/` 下的某个目录，在 `/boot/config/go` 里软链过去
- 或者干脆全放容器里（本方案的做法）

### 坑 11：`/var/log` 是 128MB tmpfs，写满会阻塞整个系统

**背景**：Unraid 的 `/var/log` 是内存盘，128MB。写满后 rsyslog 报 `No space left on device`，然后**整个系统的日志记录停止**，后续故障全查不到。

**历史事故**：2026-10-16，一个缺失的 `question.png` 导致 nginx 每次开 Dashboard 刷 404，单文件灌 15.5 万行写满 tmpfs。

**解法**：容器日志统一配 `json-file` driver + `max-size`/`max-file` 限流（本方案 compose 已配好）。

如果已经满了：
```bash
df -h /var/log
# 压缩输出到磁盘（不要就地 gzip，满了写不下）
gzip -c /var/log/syslog > /mnt/disks/nvme/logs-archive/253-var-log-$(date +%Y%m)/syslog.gz
> /var/log/syslog
```

### 坑 12：RAGFlow 占满 GPU 显存

**症状**：`nvidia-smi` 显示 19GB 显存已用，GPU 利用率 0%。

**根因**：RAGFlow 的 4 个 `task_executor` 进程各占 4-5GB，加起来 19GB，即使没任务也不释放。

**解法**：
```bash
cd /mnt/disks/nvme/docker/ragflow
docker compose -p ragflow -f docker-compose.yml --env-file .env \
  --profile elasticsearch --profile gpu stop
```

停完 `memory.used` 归零，可用内存从 10GB → 36GB。

**恢复**：同命令 `up -d`。

## 2026-10-20 · Docker / Compose

### 坑 13：`--runtime=nvidia` 与 `--gpus all` 行为不同

**现象**：
```bash
docker run --rm --runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=all alpine nvidia-smi
# ERROR: driverInitFileInfo 578 result=11 ... exec /usr/bin/nvidia-smi: no such file or directory
```

**根因**：`alpine` 里没装 nvidia-smi。`--runtime=nvidia` 只注入驱动库，不注入工具。

**正确做法**：用带 CUDA 工具链的镜像验证：
```bash
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi -L
# GPU 0: NVIDIA RTX A5000 (UUID: GPU-...)
```

**compose 里用 `deploy.resources.reservations.devices`**（本方案的做法），等价于 `--gpus all`，比 `--runtime` 更标准。

## 2026-10-21 · Wan2.2 低光/夜景明显欠曝

**症状**：同一提示词 "Empty street at night, rain reflecting neon signs"，
H3 出的夜景亮度正常，Wan2.2 出的偏黑，暗部细节几乎全丢。

**根因**：Wan2.2-5B 的 FP16 权重在暗场景上动态范围压缩更明显；
另外 CFG 3.5 + simple scheduler + 6 步的组合对低对比场景偏保守。

**解法（按性价比排序）**：
1. 提示词补救：加 `well lit by neon signage` / `visible details in shadows` /
   `bright practical lights`，别只写 `night`
2. 路由补救：夜景/低光镜头强制 H3（代价是慢 4 倍）
3. 后期补救：`ffmpeg -vf "eq=brightness=0.06:contrast=1.06:saturation=1.05"`

**当前状态**：`router.py` 未处理该场景，属已知短板。

**验证**：抽帧对比 `E01_final.mp4` 的镜1/镜4（Wan2.2）与镜2/镜3（H3）亮度。
