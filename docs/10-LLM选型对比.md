# LLM 选型对比（分镜任务实测）

测于 2026-10-22，icompify 中转 `https://api.icompify.com/v1`。
被测模型：`deepseek-v4.1-flash` / `deepseek-v4-pro` / `glm-5.3` / `glm-5.3-flash`。

---

## 一、怎么测的

用**同一份真实分镜任务**压测，不是跑分玩具：

- 输入：200 字废土剧本（4 个角色、3 句对白、一场打斗）
- 模板：线上正在用的 `storyboard_v2`（中文、H3 规则、JSON 输出）
- 参数：temperature 0.5，max_tokens 16384（Pro 给 32768），每模型跑 2 轮
- 判分维度：

| 维度 | 含义 |
|---|---|
| JSON 合规 | 输出能否直接 `json.loads`（不用二次修补） |
| engine 合规 | 每个镜头是否都填了合法 `engine` |
| 镜头数 | 是否按 max_shots=8 拆分 |
| 台词保真 | 剧本里 3 句关键台词是否原样出现在 `dialogue`（/3） |
| 中文占比 | prompt 里中文字符占比（应 >0.85） |
| 提示词均长 | 单镜 prompt 平均字数（太短=信息不足） |
| 输出/推理 token | 成本与延迟的直接来源 |

脚本：`scripts/llm_bench.py`，明细 `scripts/llm_report.py`。

## 三、结论（一句话版）

| 场景 | 选谁 |
|---|---|
| **日常主力（分镜/大纲/转中文）** | **DeepSeek 4.1 Flash** —— 快 10-30 倍，质量打平 |
| 关键集（要做精品、不赶时间） | GLM 5.3 —— 提示词最长最细（148 字），代价是 4.6 分钟/次 |
| 降级备用 | GLM 5.3 Flash |
| **不建议** | DeepSeek 4 Pro —— **单次 14 分钟**，只为一个分镜，产能上不可接受 |

### 为什么 4 Pro 不能当主力

| 项 | 数据 |
|---|---|
| 单次分镜耗时 | **13.6-14.3 分钟** |
| 推理 token | 6,024-7,283（**占总输出 79-87%**） |
| 提示词质量 | 反而最短（70-111 字），不比 Flash 好 |
| 一台 24 集会多花 | 24 × 14 分 ≈ **5.6 小时纯等待** |

它把 80% 的 token 花在"思考"上，但分镜这种结构化改写任务并不需要长链条推理。
用它做分镜是拿推理能力换等待时间，性价比最差。

### 为什么 GLM 5.3 值得留一手

| 项 | GLM 5.3 | DeepSeek 4.1 Flash |
|---|---|---|
| 提示词均长 | **148 字** | 130 字 |
| 中文占比 | 0.90 | 0.90 |
| 稳定性 | 2/2，波动 14 秒 | 2/2，波动 11 秒 |
| 延迟 | 4.6 分钟 | **27 秒** |

GLM 5.3 写得更细（多 14% 信息量），对"人物服装/道具细节"描述更full。
适合：定妆集、重头戏、需要一次到位不返工的集。
不适合：批量生产（每集 40 镜要调用 1-2 次，4.6 分钟/次 × 24 集 = 1.8 小时）。

### GLM 5.3 Flash 的位置

延迟 299 秒（波动大，最慢 362 秒）、提示词 105 字 —— 比 GLM 5.3 慢且更短，**两头不占**。
唯一价值是当 GLM 5.3 限流/失败时的备用；中文占比最高（0.91）但信息量不足。
**不建议做主力，也不建议做降级首选**（降级用 GLM 5.3 更划算）。

## 四、参数建议

### 4.1 推荐配置（写进 `config/prompts.yaml`）

```yaml
llm:
  base_url: https://api.icompify.com/v1
  default_model: deepseek-v4.1-flash     # 主力：27 秒/次，质量打平
  fallback_model: glm-5.3                # 降级：慢但更细，Flash 挂了才用
  temperature: 0.5                       # ★ 从 0.6 降到 0.5
  max_tokens: 16384                      # ★ 从 65536 降到 16384
  context_length: 262144
  timeout_sec: 600
```

### 4.2 为什么这样设

| 参数 | 建议值 | 理由 |
|---|---|---|
| `temperature` | **0.5** | 0.6 时两轮分镜的镜头数会在 7/8 间跳（实测），0.5 更稳；再低（0.3）会退化成语焉不详 |
| `max_tokens` | **16384** | 实测单次分镜输出 3,200-3,600 token，40 镜最多约 12K；设 64K 只是把"提前截断"的风险换成"模型啰嗦"的风险 |
| `timeout_sec` | **600** | 主力 27 秒足够；留 600 是给降级模型（GLM 5.3 约 290 秒）余量 |
| `context_length` | 262144 | 保持，用于输入长度预检 |

### 4.3 分阶段用不同模型（可选进阶）

如果想让关键集更好、日常更快，可以按阶段分模型：

```yaml
prompts:
  llm_by_task:
    outline: deepseek-v4.1-flash      # 大纲：快就够
    baseinfo: deepseek-v4.1-flash     # 锁信息：结构化抽取，Flash 足够
    storyboard: deepseek-v4.1-flash   # 分镜：主力
    storyboard_quality: glm-5.3       # 精品集：手动切
    localize: deepseek-v4.1-flash     # 批量转中文：要快
```

界面上加一个「本集用精品模型」的开关即可，不用全局改。
（这一项尚未实现，如需要我可以加。）

### 4.4 千万别设的

| 设置 | 后果 |
|---|---|
| `deepseek-v4-pro` 做默认 | 每次分镜 14 分钟，一集要调用 1-2 次 |
| `max_tokens` < 8192 | 40 镜的分镜会被截断，JSON 解析失败 |
| `temperature` > 0.8 | 镜头数、engine 字段开始乱跳 |
| `timeout_sec` < 300 | GLM 降级时会误判超时 |

## 五、给老板的选择

**A（推荐，默认就用这个）**：`deepseek-v4.1-flash` + `glm-5.3` 降级，参数如上。
→ 27 秒/次，24 集分镜总共约 11 分钟。

**B（精品路线）**：日常 Flash，关键集手动切 GLM 5.3。
→ 关键集多花 4 分钟/次，换 14% 更细的提示词。

**C（全 GLM 5.3）**：统一用 GLM 5.3。
→ 24 集多花 1.8 小时，但风格最统一。

**D（不推荐）**：DeepSeek 4 Pro 做主力。
→ 24 集分镜多花 5.6 小时纯等待，提示词反而更短。
